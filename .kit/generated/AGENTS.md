# art-studio 專案規範（`AGENTS.md`）

本檔是規劃者（Claude）與實作者（Antigravity）共用的唯一規則檔，由初始化套件 v0.2.7 產生。`CLAUDE.md` 只寫 `@AGENTS.md`，`GEMINI.md` 只寫「請遵守 AGENTS.md」。要改通用規則請改套件；本專案專屬的規則寫在第 10 節。

## 1. 熱區（開工前必讀）與冷區

- 熱區：本檔、`docs/collaboration-protocol.md`、`docs/adr/`、`specs/`、`project.config.json`、自己這張單的內文與留言。
- 冷區（預設不讀）：`docs/archive/`、`specs/archive/`。

## 2. 角色

| 角色 | 擔任者 | 負責 | 禁止 |
| :--- | :--- | :--- | :--- |
| 決策者 | 使用者 | 方向、核准規則與大級變更、人工驗收、實機測試 | — |
| 規劃與驗收 | Claude | 寫規格與 ADR、開單、先寫並鎖定驗收測試、派工、審證據包與程式差異、合併 | 修改業務程式 |
| 協調者 | 常駐對話（Orchestrator），開場領代號 | 找單、接單、建工作資料夾、分派實作子代理與驗收員（要求子代理定期回報階段與 `--agent` 代號） | 自己寫程式 |
| 實作 | 實作子代理，每張單一個 | 依單實作、跑必跑檢查、交件報告 | 自行關單、修改驗收測試與鎖定檔、未 `status:ready` 就動工 |
| 驗收員 | 交件後另外叫起的子代理，留言第一行 `🧪 驗收員` | 跑驗收、張貼證據包、逐條對照驗收條件、有畫面時做視覺審查 | 修改任何檔案、由實作的同一個子代理擔任 |

## 3. 自主作業原則

- **Claude 可以自己決定**：在既有規格與 ADR 範圍內的技術細節；寫或改驗收測試（派工前）；拆單、排序；核准寬鬆授權（MIT、Apache-2.0、BSD、ISC、Zlib、Unicode）的依賴並記錄；驗收通過後合併。
- **必須問使用者**（留言時寫明第幾類）：① 改變業務行為的選擇；② 非寬鬆授權的依賴、字型、模型、資料集；③ 退回 3 次後要改規格語義；④ 需要真人或實機的測試；⑤ 預算、法務、對外發布；⑥ 推翻已接受的 ADR 或決策；⑦ 大級能力變更；⑧ 系統層級環境變更。
- **絕對不做**：見第 5 節。

## 5. 絕對禁止

| 禁止 | 原因 |
| :--- | :--- |
| 修改、刪除 `tests/acceptance/`、`*/tests/acceptance_*`、單上列為鎖定的檔案 | 驗收測試由 Claude 鎖定，驗收時比對鎖定 commit |
| 修改本檔、`docs/`、`specs/`、`project.config.json`（單上明確要求者除外） | 規則與規格由規劃者決定 |
| 未經核准新增、升級、移除依賴 | 授權與供應鏈 |
| 針對測試資料寫死特例、偵測測試環境、跳過或忽略測試 | 視為作弊，直接退回 |
| 直接提交到 `main`、強制推送、改寫已推送的歷史 | 可追溯性 |
| 在程式、測試、fixture 放密碼、Token、密鑰、真實個資 | 安全；密鑰一律讀環境變數或本機設定 |
| 啟動不會自己結束的程序卻不加逾時 | 會卡住常駐對話 |
| 驗收時接到開發者自己在用的外部服務（資料庫、佇列、第三方 API） | 驗收要可重現；外部服務由腳本起、跑完收乾淨 |

## 6. 程式碼規範（通用）

- 單檔軟上限 1,200 行、硬上限 1,800 行。
- 註解三不寫：不寫語法說明、不寫重複型別的舊式註解（例如 `@param {Object}`）、不留已廢棄的名詞。
- 註解三必寫：檔頭寫 `@module`／`@role`／`@forbid`（這個模組不准做什麼）；不直覺的地方寫 `@why`；校準過、改了容易出事的程式標 `@lock: <理由>`。要改 `@lock` 的程式，單的內文要有 `## 解鎖` 段落列出並由使用者核准。`task accept` 檢查改到的檔案。
- 重用階梯：先組合現有的，再擴充，最後才新增；移除舊入口要一起清掉沒人用的程式。
- 不寫死：參數走「設定 → 狀態 → 單一讀取函式」，不針對特定名稱寫特例、不散落魔法數字；專案可在設定的 `forbiddenPatterns` 列出要擋的寫法。
- 零閹割：不得為了縮小體積或湊行數而簡化業務邏輯、縮水功能。
- 建置產物不進版本控制（設定的 `generatedPaths` 列出的除外）。
- 函式庫不得 `unwrap / expect / panic`（或該語言的等價寫法）；錯誤用具名型別。
- 狀態判斷只比對 ID 與列舉碼，不得對顯示文字做模糊比對。
- 同一邏輯只寫一份；共用函式放在明確的模組。
- 同一個事實只記一處：版本號、清單、登記表等不要在多個檔案各抄一份，要用就去讀那一處。非記多處不可時，要有工具負責同步，並有檢查比對一致（例如 `kit-check`、`docs-check`），不靠人記得一起改。
- 行數上限的用意：單檔上限是避免產生龐大的檔案，單張單的業務程式上限（`businessLineLimit`）是讓每張單的改動小到審得完、出錯好回頭，都不是要把程式寫短。超過時停下來在單上留言，提出拆單方式或申請放寬（寫理由，規劃者決定後在內文寫 `業務程式上限：N 行`）；不得用一行塞多個陳述、刪註解、刪測試或改寫範圍外的程式來湊行數。
- 用格式檢查守住「一行一個陳述」（例如 ESLint `max-statements-per-line`、rustfmt），讓行數反映真實規模。

## 7. 協作（必讀 `docs/collaboration-protocol.md`）

- 留言第一行標身分：Claude 寫 `🤖 Claude`，實作寫 `🛠️ <代號>`，驗收員寫 `🧪 驗收員`；沒有標記的留言視為使用者本人。
- 常駐接單、交件、驗收、合併一律用 `task` 工具；每張單在自己的工作資料夾做，不在主資料夾切分支。
- 有問題在單上留言後用 `task wait <N> --worker <代號>` 等回覆（自動切為 `blocked`），不要停下來等人打字；實作子代理開始跑檢查時回報 `checking`，每 10 分鐘至少用 `task heartbeat --worker <代號> --ticket <N> --phase <階段> --agent <子代理代號>` 回報一次。

## 8. 提交前必跑

見 `project.config.json` 的 `checks`（依倉庫特性組合）；`task accept` 會一併跑。

## 9. 溝通用語
